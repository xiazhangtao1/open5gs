# 四用户、四 Session Worker 吞吐汇总

配置为 UPF 4 个 Session Worker、7 个逻辑 CPU，N3/N6 各 4 条 memif 队列；
VPP 保持 2 个逻辑 CPU、1 个转发 Worker。四个真实用户各有一个 PDU/PFCP
Session，并分别占据 Workers 0–3。配置覆盖见 [helm-overrides.yaml](helm-overrides.yaml)。

四用户同时发流，上下行分别测量。每用户一个 iperf 进程、4 条传输流，
总共 16 条传输流；每方向测量 30 秒、预热 3 秒。速率为接收端应用有效
载荷的十进制 Gbit/s，数据绕过无线协议栈及物理网线。

| 口径 | 总上行 | 总下行 |
| --- | ---: | ---: |
| TCP，两轮平均 | 21.730 | 21.853 |
| TCP，两轮最高观测 | 21.778 | 21.925 |
| UDP，重复通过的发送档位 | 25.500 | 28.000 |
| UDP，末次实际接收 | 25.498 | 27.998 |
| UDP，末次总丢包率 | 0.009333% | 0.007085% |

UDP 两档各有两轮通过；最差用户丢包率分别为 0.009727% / 0.008160%。
通过标准为总丢包及每用户丢包率均 ≤0.1%，且每用户实际发送在目标的 ±1%
内。每用户发送档位约为 6.375 / 7 Gbit/s。

TCP 使用 iperf3 3.22，最终 UDP 两端使用单线程 iperf3 3.15，UDP 载荷为
1400 字节。测试端采用四 Worker、四队列接入，每端点允许使用两个物理核。
原有 UPF 转发源码保持不变。

较高的 26 / 28.5 Gbit/s UDP 探测既未发满目标，又出现丢包超标。因此表中
UDP 值是本轮按 0.5 Gbit/s 步长扫描后重复通过的档位，绝对上限尚未确定。
相比单 Worker 的历史数据，本轮也增加了 CPU、队列与测试端资源，并调整
UDP 工具版本，不能将差异仅归因于 Worker 数量。

会话处理负载已分散到四个 Worker。诊断采样中，核心 VPP 唯一转发 Worker
约 78.57% 的用户态采样权重位于 memif 收发函数；VPP 及单 N3/N6 dispatcher
仍是扩展限制。正式窗口中没有新增 CPU 配额节流或内存分配失败。

测试后保留四 Worker 配置，删除临时测试接入，恢复无线侧原始绑核。
四个真实 UE 各自 ping 验证 5/5 成功。
