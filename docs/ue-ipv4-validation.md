# UE IPv4 子网、网关统一配置验证

验证日期：2026-10-08 至 2026-10-09。

## 实现与兼容性

新增两个 Helm 参数，均有默认值，不要求用户填写：

```yaml
networking:
  ue:
    ipv4Subnet: 10.45.0.0/16
    ipv4Gateway: 10.45.0.1
  smf:
    ipv4PoolRanges: []
```

同一份子网、网关用于 SMF 和 UPF 的 IPv4 session 配置、TUN 接口及
IPv4 NAT 源网段、VPP N6 内侧 memif 的地址/前缀。外侧
`vpp.n6.externalAddress` 和 `vpp.n6.defaultGateway` 的含义保持不变。
没有修改核心网 C 转发代码或 IP 分配算法。

Helm 渲染时验证 IPv4 格式、规范网络地址、`1..30` 前缀、网关属于子网
且不是网络/广播地址。显式动态范围最多 16 个，必须是有序的 `start-end`，
属于子网且避开网关、网络/广播地址，不允许范围重叠。
空列表保持 SMF 默认池行为。静态订阅需要人工检查：地址应属于子网、
避开网关和动态范围；Helm 不读取 MongoDB。

`vpp.n6.interfaceAddress` 默认改为空，自动生成网关/前缀；已有显式值
在 VPP 启用时必须与共享配置一致。TUN 启动脚本接收 `UE_IPV4_SUBNET`
和 `UE_IPV4_GATEWAY`，缺省仍使用旧值。脚本管理 `ogstun` 的 IPv4 地址，
变更子网时清理该接口之前子网对应的匹配 NAT 规则，保留其他接口、规则
和 IPv6 配置。重复执行不会累积地址或同一条 NAT 规则。

## 实际部署测试配置

在现有 Kubernetes 环境依次部署 TUN（revision 155）和 VPP memif
（revision 156），都使用下列新子网。特意改变前缀并使用非 `.1` 网关：

```yaml
networking:
  ue:
    ipv4Subnet: 10.66.12.0/24
    ipv4Gateway: 10.66.12.254
  smf:
    ipv4PoolRanges:
      - 10.66.12.10-10.66.12.99
      - 10.66.12.110-10.66.12.199
```

现有 OAI UE 使用旧子网静态地址 `10.45.0.3`，测试新子网期间暂停辅助 UE，
没有修改它的订阅。使用受控 NGAP/NAS/GTP-U 对端、真实核心 NF 和 MongoDB，
临时测试 IMSI 为 `460110000009050`，诊断复验另使用 `460110000009060`。
受控 gNB 的临时 N3 地址为 `10.2.0.233`。

TUN 实际接口为 `ogstun 10.66.12.254/24`，主机生成对应直连路由和
`10.66.12.0/24` 的 masquerade 规则；原 `10.45.0.0/16` 的匹配规则已删除。
重复运行新启动脚本后仍只有一个 IPv4 地址和一条该子网的 NAT 规则。
测试日志中的动态 UE 地址全部属于配置范围。

memif 实际使用两张 SR-IOV iAVF VF，VPP 有 2 个 Worker，UPF 有 2 个
Session Worker；N3、N6 memif 各有 2 个 RX/TX 队列且连接成功。
VPP `memif1/0` 实际地址为 `10.66.12.254/24`；N3/N6 外侧分别为
`10.2.0.231/20`、`10.2.0.232/20`，外部下一跳为 `10.2.7.254`。
UPF N3 为 `10.2.0.230`。切换到 memif 前删除了 TUN 模式添加的主机
`10.2.0.230/32` 地址，避免主机本地路由截获应到 VF 的报文。

## 验收结果

| 场景 | 结果 |
| --- | --- |
| TUN → 新网关 `10.66.12.254` | 100 次顺序、100 轮双会话并发，共 300 次承载生命周期，通过 |
| TUN → 外网 `8.8.8.8` | 同样 300 次，通过 |
| 双 VF memif → 新网关 | 同样 300 次，通过 |
| 双 VF memif → 外网 | 同样 300 次，通过，实际经过 N6、VPP NAT44、DPDK 外侧接口 |
| memif 重启后新网关/外网 | 刷新测试主机 N3 邻居后，两组完整协议冒烟均通过 |

两种模式的新地址压力合计 1200 次生命周期。每组都包含真实回包校验、
合法/非法优先级、修改/取消覆盖及双会话隔离，退出码均为 0。
运行命令如下，依次替换目标和部署模式；每个测试进程结束后再运行下一组：

```bash
docker exec \
  -e XCN_QOS_PCF_URL=http://10.2.0.119:30777 \
  -e XCN_QOS_TEST_MSIN=0000000905 -e XCN_QOS_CYCLES=100 \
  -e XCN_QOS_PING_IP=10.66.12.254 \
  -e XCN_FORWARDING_GNB1_ADDR=10.2.0.233 \
  xcn-ue-ipv4-test /open5gs/build/tests/vonr/vonr \
  -q -c /results/qos-live.yaml dedicated-bearer-test
```

TUN 和最终 memif 压力各连续观察 300 秒、11 个样本，所有 Pod 保持就绪，
没有非计划重启。资源区间如下；压力期间包含正常分配增长，不能解释为
全程 RSS 不增长：

| NF | TUN RSS（KiB） | TUN FD | memif RSS（KiB） | memif FD |
| --- | --- | --- | --- | --- |
| AMF | 60512–144512 | 36–37 | 79244–137876 | 36–37 |
| SMF | 154408–172960 | 29 | 161056–178048 | 29 |
| PCF | 25956–34820 | 25 | 32036–40208 | 25 |
| UPF | 129832–134056 | 11 | 183116–202336 | 30 |
| VPP | — | — | 1517148–1533340 | 53 |

memif 压力结束后的 180–300 秒采样中，五个进程的 RSS 均保持不变。
两个 UPF Worker 实际均处理了数据，drops、queue-full、push-fail 为 0；
N6 两个 RX 队列均有数据，RX/refill、dispatch-drop 和 N3/N6 TX drop 为 0。
N3 的 invalid 计数包含首轮探测期间的 3 个包，后续最终压力未新增；
不把该累计计数写为 0。DPDK 接口还接收共享网络的广播等背景流量，
其累计 drops 不等于本次 UE 数据的丢包率。

## 恢复原配置

最终 Helm revision 157 保留正式 memif 模式和新运行镜像，恢复默认
`10.45.0.0/16`、`10.45.0.1`，动态范围恢复为
`10.45.1.2-10.45.255.254`。验证实际 ConfigMap、VPP `memif1/0` 和主机
原 `ogstun` 地址一致，临时 `10.66.12.0/24` NAT 规则已清理。
原 OAI UE 已恢复为 `10.45.0.3`，订阅内容未修改。

恢复后的本地网关承载压力 300 次通过，与 OAI 并行运行；随后为抓包定位
又完成同样的 300 次，均校验 TEID/QFI 和真实 ICMP 回包。
OAI 首次网关冒烟 3 次回复 2 次，外网冒烟 3/3；后续网关持续 ping
300/300、0% 丢包。外网第一轮持续 ping 为 293/300，7 个未收到回复的
序号为 `6、7、16、17、126、127、128`，不报告为零丢包。
恢复后的受控外网压力也曾出现单包超时；之后独立外网协议冒烟通过，
没有将失败的那轮记为通过。本地网关压力与外网抓包对照分别验证。

随后在再次运行 300 次承载压力的同时，采集 VPP 全路径抓包，并让 OAI
UE 和主机直接经 `ens5f0` 分别 ping 外网 300 次。两者均为 297/300。
OAI 缺少序号 `193、194、198`，主机直连缺少 `196、197、201`。
逐跳核对 OAI 的 ICMP 标识和序号，结果如下，重复捕获按序号去重：

| 抓包位置 | 唯一 ICMP 序号数 | 缺少序号 |
| --- | --- | --- |
| N3 上行 GTP-U，UE → UPF | 300 | 无 |
| N6 外侧发出，VPP NAT44 → 外网 | 300 | 无 |
| N6 外侧收到，外网 → VPP | 297 | 193、194、198 |
| N6 内侧，VPP → UPF | 297 | 同上 |
| N3 下行 GTP-U，UPF → gNB | 297 | 同上 |
| OAI UE 实际收到 | 297 | 同上 |

本轮缺失回包尚未进入 N6 接收路径，核心收到的 297 个回包全部送达 UE；
主机直连对照也丢包，支持共享外网路径/ICMP 响应波动的判断。
这轮没有发现核心网内部转发丢包。第一轮 7 次丢包没有同步抓包，不能
据后一轮结果逐包断言第一轮的具体丢包位置。
`final-path.pcap` 共 50000 条记录，包含完整 `1..300` 探测序列；
逐跳统计保存在 `path-analysis.json` 和 `path-analysis.log`。

恢复后另连续观察 300 秒，所有 Pod 保持就绪，无新增重启；SMF FD 为 29，
UPF 为 30，VPP 为 53，AMF 随测试连接为 36–37，PCF 建立连接后为 25。
测试释放后 SMF 仅剩原 OAI 的 1 个会话，临时订阅计数为 0。
本次测试容器与临时 gNB/N3 主机别名清理后，`ens5f0` 仅保留原
`10.2.0.119/20` 地址。

## 证据与测试边界

原始日志、配置、资源采样及诊断抓包保留在本机
`/tmp/xcn-ue-ipv4-results/`，大文件没有提交到 Git。
验证使用此前的 dedicated-bearer 测试程序，独立校验实际 GTP-U TEID/QFI、
内层 IPv4 源/目的地址及 ICMP Echo Reply，同时检查承载创建、优先级修改、
取消覆盖、access 恢复、并发双会话和删除。

测试程序应在 `/open5gs/build/tests/vonr/vonr` 运行，保持构建目录的 RPATH
及同一构建的动态库。首次搬到 `/results` 后误加载系统旧库，导致 TUN QFI
解析断言失败；抓包确认实际回包 QFI 正确，放回构建目录后两组完整重跑通过。
一次提前启动的第二测试进程因共享 AF 端口冲突退出，也未计为通过。
memif 首轮首次探测超时，核心 NF 未重启；随后诊断抓包复验通过，进入
memif 的 IP/UDP 校验和正确。重启复验又观察到首次探测超时，VPP N3
memif 抓包没有收到该轮流量，测试主机 N3 邻居随后处于 FAILED 状态。
VF 重新分配还实际出现了 N3 MAC 改变。定向刷新测试主机的单个 N3
邻居后，抓包确认 ARP 请求/应答正常，重启后的网关和外网复验均通过。
这表明该测试网络需要在 VF 重建后重新收敛邻居/交换路径。
核心网报文校验及首次探测最多三次的重试限制保持不变。
测试环境使用的针对性刷新命令为：

```bash
kubectl exec -n xcn deployment/xcn-5gc -c upf -- \
  ip neigh del 10.2.0.230 dev ens5f0
```

此命令仅适用于本次测试主机和 N3 地址，不能盲目套用于其他部署。
验收以最终完整重跑和网络准备后的重启复验为准。

测试不是无线调度器验证，也不覆盖 IPv6 N6、线速性能或长期内存泄漏排除。
